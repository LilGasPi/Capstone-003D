# Metodología declarada y justificada

## 1. Metodología seleccionada

Para el desarrollo de Estacionando se declara el uso de **Scrum adaptado a contexto académico**, complementado con prácticas de Kanban para visualización del flujo de trabajo y control de pendientes.

La metodología se aplica de forma incremental, organizada por fases y sprints cortos. Cada sprint permite priorizar funcionalidades, construir incrementos funcionales, revisar avances, detectar bloqueos y ajustar el roadmap del producto.

## 2. Justificación de la elección

Scrum fue seleccionado porque el proyecto Estacionando presenta características propias de un producto digital en evolución:

- Requisitos que cambian o se refinan con feedback docente y pruebas de usuario.
- Necesidad de entregar avances funcionales por etapas.
- Desarrollo de flujos diferenciados para conductor, anfitrión y sistema.
- Alto valor en demostrar software funcionando, no solo documentación.
- Trabajo colaborativo entre integrantes con responsabilidades distribuidas.
- Necesidad de distinguir claramente lo implementado de lo pendiente.

Scrum permite gestionar el proyecto mediante backlog, sprints, Definition of Done, retrospectivas y revisión de incrementos. Kanban se utiliza como apoyo para visualizar estados como Pendiente, En progreso, En revisión, Terminado y Pendiente de mejora.

## 3. Adaptación al contexto académico

El equipo no implementa Scrum de forma empresarial completa, sino una versión adaptada a la realidad del proyecto académico. La adaptación considera:

- Sprints alineados a fechas de entrega del curso.
- Product Owner asumido por el equipo según visión del producto y feedback docente.
- Scrum Master rotativo para coordinar tareas, fechas y bloqueos.
- Equipo de desarrollo compuesto por los integrantes del proyecto.
- Revisión de sprint vinculada a demos, entregas y observaciones de la profesora.
- Retrospectiva documentada después de cada hito relevante.

## 4. Roles del equipo

| Rol Scrum adaptado | Responsable funcional | Descripción |
|---|---|---|
| Product Owner | Equipo Estacionando | Define prioridades según valor de negocio, alcance académico y feedback docente. |
| Scrum Master | Rol rotativo | Facilita coordinación, seguimiento, reuniones internas y resolución de bloqueos. |
| Development Team | Integrantes del proyecto | Diseñan, documentan, desarrollan, prueban y presentan el avance. |
| Stakeholder principal | Docente / comisión | Evalúa avance, metodología, cumplimiento y claridad de presentación. |
| Usuarios objetivo | Conductores y anfitriones | Personas que buscan estacionar o publicar espacios disponibles. |

## 5. Eventos utilizados

| Evento | Aplicación en el proyecto |
|---|---|
| Sprint Planning | Se priorizan funcionalidades y evidencias para la próxima entrega. |
| Daily / seguimiento breve | Revisión rápida de avances y bloqueos por chat o reunión. |
| Sprint Review | Se valida el incremento mediante demo o revisión documental. |
| Sprint Retrospective | Se documenta qué funcionó, qué falló y qué se ajustará. |
| Backlog Refinement | Se reordenan historias y se separa lo implementado de lo pendiente. |

## 6. Artefactos utilizados

| Artefacto | Uso |
|---|---|
| Product Vision | Define propósito, usuarios, problema y propuesta de valor. |
| Product Backlog | Lista priorizada de épicas, historias y tareas funcionales. |
| Sprint Backlog | Subconjunto del backlog comprometido para la siguiente entrega. |
| Incremento | Avance funcional demostrable del aplicativo. |
| Definition of Done | Criterios mínimos para declarar una tarea terminada. |
| Retrospectivas | Registro de aprendizajes y acciones de mejora. |
| Roadmap | Secuencia de evolución del producto por fases. |

## 7. Forma de trabajo declarada

1. Se define o ajusta el objetivo del sprint.
2. Se seleccionan historias del Product Backlog según prioridad.
3. Se distribuyen tareas entre integrantes.
4. Se desarrolla el incremento funcional o documental.
5. Se valida contra la Definition of Done.
6. Se prepara demo, documentación y presentación.
7. Se revisa feedback docente.
8. Se documenta retrospectiva y se ajusta el backlog.

## 8. Justificación final

Scrum adaptado es adecuado para Estacionando porque permite demostrar avances progresivos, responder a observaciones de la profesora, mantener trazabilidad de lo realizado y ordenar el roadmap restante. Además, facilita evidenciar el avance real del software sin presentar como terminadas funciones que aún pertenecen a fases posteriores.
